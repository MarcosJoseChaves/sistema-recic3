# Etapa H2C.3A — Especificação técnica do schema da baseline nuclear

## 1. Situação, fontes e limites

**Situação: APROVADA TECNICAMENTE em 31/07/2026.** As 30 decisões técnicas foram
aprovadas. A aprovação é conceitual: tabelas, migrations, SQL, constraints,
índices, bootstrap, permissões e interfaces ainda não foram implementados.

Foram confrontados os documentos funcionais H2C.2D–H2C.2J, mapa e comparação do
schema, plano da baseline, código versionado, testes e migrations 001–011. Não
houve acesso a banco, dump, `.env`, `DATABASE_URL`, dados reais ou serviços. Não
foi escrito ou executado SQL e nenhuma migration foi criada ou alterada.

## 2. Princípios técnicos

- instalação exclusiva em PostgreSQL vazio, validado antes do primeiro DDL;
- migrations aplicadas são imutáveis e qualquer evolução gera novo arquivo;
- nenhuma adaptação silenciosa, `DROP`, `TRUNCATE` ou carga de dado real;
- integridade referencial no banco sempre que a relação for representável;
- autorização e validações contextuais permanecem no servidor;
- histórico financeiro, patrimonial, cadastral e de solicitações não é apagado;
- documento privado guarda metadados e chave opaca, nunca o binário no banco;
- migrations 001–011 e suas 23 tabelas `fc_*` permanecem como fontes históricas;
- a condição mais restritiva prevalece quando banco e regra de negócio se somam.

## 3. Convenções técnicas aprovadas

| Tema | Alternativas consideradas | Decisão aprovada | Justificativa |
|---|---|---|---|
| idioma | português; inglês; misto | português técnico | coerência com o sistema e domínio |
| número | singular; plural | plural para tabelas | padrão dominante atual |
| grafia | camelCase; snake_case | `snake_case` | compatibilidade PostgreSQL/Python |
| PK/FK | nomes livres; padrão | `id` e sufixo `_id` | leitura e automação previsíveis |
| constraints | automáticas; explícitas | `pk_`, `fk_`, `uq_`, `ck_` | diagnóstico seguro |
| índices | automáticos; explícitos | `idx_<tabela>_<finalidade>` | intenção verificável |
| códigos | texto livre; técnico | maiúsculas ASCII com `_` | estabilidade e integração |
| tempo | sem fuso; com fuso | `TIMESTAMPTZ` para instantes | eventos consistentes |
| datas civis | timestamp; data | `DATE` | evita deslocamento de calendário |
| auditoria | campos em tudo; por categoria | campos conforme natureza | evita redundância |
| concorrência | bloqueio; versão; híbrido | `versao_registro` + lock em fluxos críticos | conflitos detectáveis |

Nomes físicos finais seguem para revisão independente. Grafia oficial é preservada em `nome`; busca
usa coluna normalizada mantida pela aplicação, sem exigir `unaccent`.

## 4. Identificadores

Foi aprovado o modelo híbrido:

- `usuarios.id` continua `INTEGER`, pela compatibilidade com o código e com as
  FKs `INTEGER` das migrations 001–011;
- novas tabelas usam `BIGINT GENERATED BY DEFAULT AS IDENTITY`;
- as 23 tabelas `fc_*` preservam `BIGSERIAL` nas migrations históricas;
- FKs sempre repetem exatamente o tipo da PK referenciada;
- UUID não é PK geral; pode ser chave pública opaca de documento/request quando
  houver necessidade de não expor sequência interna.

Converter `usuarios.id` ou os IDs `fc_*` agora teria custo e risco maiores que o
benefício. Uma conversão futura exigiria migration própria e ensaio completo.

## 5. Tipos padrão propostos

| Conceito | Tipo proposto | Regra |
|---|---|---|
| PK nova | `BIGINT IDENTITY` | positiva e não reutilizada |
| FK para usuário | `INTEGER` | compatível com `usuarios.id` |
| código | `TEXT` | CHECK de preenchimento/formato; tamanho só se houver limite real |
| nome/descrição | `TEXT` | `BTRIM(valor) <> ''` quando obrigatório |
| username/e-mail | `TEXT` | unicidade por `LOWER(BTRIM(...))` |
| CPF | `VARCHAR(11)` ou `TEXT` | CHECK de exatamente 11 dígitos; único quando informado |
| senha | `TEXT` | apenas hash produzido pela aplicação |
| dinheiro | `NUMERIC(18,2)` | sem `float`; moeda brasileira inicial |
| quantidade | `NUMERIC(24,8)` | cálculo técnico sem perda prematura |
| percentual | `NUMERIC(p,s)` | precisão definida por domínio; faixa de 0 a 100 quando aplicável |
| data civil | `DATE` | competência, validade e datas administrativas |
| instante | `TIMESTAMPTZ` | padrão `CURRENT_TIMESTAMP` quando criação |
| estado/código | `TEXT` | CHECK ou FK conforme estabilidade |
| fotografia | `JSONB` | objeto validado por versão/tipo na aplicação |
| chave privada de arquivo | `TEXT` | opaca, única, nunca URL permanente |
| checksum | `VARCHAR(64)` | SHA-256 hexadecimal minúsculo e comprimento exato |
| versão | `INTEGER` | positiva |
| IP | `INET` | sem parsing textual manual |
| request ID | `UUID` | correlação, não segredo |

`BOOLEAN` fica restrito a fatos binários. Estados com mais de dois significados
usam código explícito.

## 6. Campos comuns por natureza da tabela

| Natureza | Campos recomendados |
|---|---|
| entidade cadastral | `criado_em`, `atualizado_em`, autores, `versao_registro`, `estado` |
| entidade inativável | anteriores + `inativado_em`, autor e motivo |
| vínculo temporal | `inicio_em`, `fim_em`, estado, autores; sem `ativo` redundante se período bastar |
| evento imutável | criação, autor, tipo, fotografia/metadados; sem atualização |
| catálogo estrutural | código, nome, estado, versão; sem dados reais |
| associação pura | FKs, período/ordem quando necessário; auditoria mínima |
| auditoria técnica | append-only, request, ator, ação, objeto, resultado e metadados seguros |

Não se propõe `ativo`, `estado` e `fim_em` juntos sem necessidade comprovada.

## 7. Controle de migrations

Tabela conceitual proposta: `schema_migrations`, central e modular.

| Coluna conceitual | Tipo | Regra |
|---|---|---|
| `id` | BIGINT IDENTITY | PK |
| `migration_id` | TEXT | único por módulo |
| `modulo` | TEXT | `NUCLEO`, `FC` ou módulo opcional |
| `versao` / `ordem` | INTEGER | positivas; ordem única por módulo |
| `checksum_sha256` | VARCHAR(64) | formato hexadecimal minúsculo e comprimento exato |
| `iniciada_em` / `concluida_em` | TIMESTAMPTZ | coerência temporal |
| `situacao` | TEXT | `EM_EXECUCAO`, `APLICADA`, `FALHA` |
| `duracao_ms` | BIGINT | não negativa |
| `erro_sanitizado` | TEXT | sem SQL completo, segredo ou dado pessoal |
| `versao_aplicativo` | TEXT | rastreabilidade |
| `dependencias` | JSONB | identificadores/versões, sem conteúdo executável |

Checksum divergente bloqueia continuação. Um lock transacional/advisory evita
dois executores simultâneos. A escolha do mecanismo ainda depende de validação.

## 9. Usuários, recuperação e autenticação

### 9.1 `usuarios`

| Coluna | Tipo/nulabilidade | Constraint/índice |
|---|---|---|
| `id` | INTEGER IDENTITY, NN | PK |
| `username` | TEXT, NN | UNIQUE funcional em `LOWER(BTRIM(username))` |
| `password_hash` | TEXT, NN | não vazio |
| `nome_completo` | TEXT, NN | não vazio |
| `email` | TEXT, nulo | UNIQUE parcial normalizada; validação na aplicação |
| `estado` | TEXT, NN | CHECK de estados técnicos aprovados posteriormente |
| `exige_troca_senha` | BOOLEAN, NN | padrão verdadeiro no bootstrap |
| `criado_em`, `atualizado_em` | TIMESTAMPTZ, NN | criação automática |
| `versao_registro` | INTEGER, NN | positiva, padrão 1 |

Não existem `role`, `uvr_acesso`, token ou expiração na instalação nova.
Tentativas de login e sessões continuam responsabilidade da camada de segurança
até uma especificação própria; não se inventa tabela nesta etapa.

### 9.2 `usuario_recuperacoes_senha`

Guarda `usuario_id`, hash SHA-256/HMAC do token, criação, expiração, uso,
invalidação, `request_id` e auditoria mínima. Token puro nunca é persistido.
Índices: hash único, usuário+expiração e expirações não usadas. Exclusão pode ser
por retenção técnica controlada porque não é fato de negócio, mas a auditoria do
evento permanece.

O último Administrador Global não é protegido apenas por CHECK: a revogação
exige transação, lock das atribuições e contagem de administradores ativos.

## 10. Perfis, permissões e escopos

Foi aprovado o modelo híbrido para manter FKs reais:

- módulos, ações e permissões formam catálogos estruturais;
- perfil agrupa permissões; perfil protegido não é apagado/renomeado livremente;
- `auth_usuario_perfis` registra perfil, validade, concedente, justificativa e
  revogação;
- escopo global é propriedade controlada da atribuição;
- associações e UVRs usam tabelas específicas com FK;
- escopo de objeto fica em tabela própria do módulo que conhece a entidade, não
  em `(tipo, id)` genérico sem FK.

Constraints: códigos únicos, perfil-permissão único, períodos coerentes, somente
um escopo global por atribuição e ausência de duplicidade ativa. Atividade de
usuário, perfil, associação e UVR, autoelevação e última administração global
exigem validação transacional no servidor.

## 11. Associações, UVRs e aliases

| Tabela | Colunas essenciais | Integridade/índices |
|---|---|---|
| `associacoes` | código, nome, estado, versão e auditoria | código único; nome normalizado indexado |
| `uvrs` | associação, código, nome, estado, início/fim e auditoria | FK associação; código único global ou composto a validar |
| `uvr_aliases` | UVR, valor original/normalizado, origem, início/fim, estado | alias normalizado único ativo |
| eventos | entidade, tipo, estado anterior/novo, motivo, fotografia e autoria | append-only; entidade+data |

UVR ativa não pode apontar para associação inativa: FK prova existência, mas a
atividade exige lógica transacional. Troca de associação cria evento/vínculo;
não reescreve história.

## 12. Associados e dados bancários

### 12.1 Cadastro e vínculos

`associados` concentra número, nome, CPF opcional, documento alternativo,
contato/endereço mínimos, estado administrativo, condição de regularização,
admissão/desligamento, referência privada de fotografia e auditoria. CPF é
somente dígitos e único quando preenchido. ATIVO exige CPF ou exceção formal;
essa regra envolve várias colunas e pode usar CHECK simples se os campos finais
forem aprovados.

`associado_associacao_vinculos` e `associado_uvr_vinculos` guardam início, fim,
tipo principal/secundário, motivo, solicitante/aprovador e autoria. Índices
únicos parciais garantem uma associação principal e uma UVR principal ativas.
Ausência de sobreposição e vínculo secundário na mesma associação exigem
constraint de exclusão por período ou validação transacional; o mecanismo físico
será conferido na H2C.3B.

Após ativação, associado usa RESTRICT e inativação/evento. Exclusão física só é
admitida para rascunho nunca ativado e sem qualquer FK/histórico.

### 12.2 `associado_contas_bancarias`

Campos: associado, banco/instituição, agência, conta, tipo, chave PIX, titular,
documento do titular, finalidade, principal, estado, validade, documento privado
e auditoria. Pode haver várias contas; índice parcial garante uma principal
ativa por associado/finalidade. Períodos são coerentes e duplicidades usam uma
chave normalizada tecnicamente definida depois.

Agência, conta, PIX, titular e documento são sensíveis: nunca entram em logs,
request metadata ou mensagens de erro. Criptografia permanece fora desta etapa.

## 13. Contas financeiras, catálogo, transações e rateios

### 13.1 Contas financeiras

`contas_financeiras` pertence obrigatoriamente a associação e guarda código,
nome, instituição, agência/conta quando aplicável, tipo, estado, abertura,
encerramento, observação e auditoria. Não representa conta bancária pessoal nem
plano contábil. Saldo inicial só será incluído se a regra futura comprovar sua
necessidade; saldos correntes são derivados de fatos financeiros.

### 13.2 Catálogo

| Tabela | Regra central |
|---|---|
| `naturezas_financeiras` | códigos estruturais `RECEITA` e `DESPESA` |
| `catalogo_grupos` | código global e nome normalizado global únicos |
| `catalogo_subgrupos` | FK grupo; código global; nome único no grupo |
| `catalogo_itens` | FK subgrupo/unidade; tipo `PRODUTO`/`SERVICO`; código global; nome único no subgrupo |
| `unidades_medida` | código, nome e precisão operacional |
| `catalogo_aliases` | alias normalizado único dentro do tipo/escopo definido |
| `catalogo_eventos` | reclassificação, substituição, inativação e fotografia |

Normalização usa coluna explícita produzida por função de aplicação comum e
validada antes de persistir; a grafia oficial não é alterada e `unaccent` não é
dependência obrigatória. Códigos nunca são reutilizados. Inativar pai não apaga
filhos; novos usos ficam bloqueados pelo servidor.

### 13.3 Financeiro e rateios

`transacoes_financeiras` guarda associação, natureza, conta, data, competência,
contraparte/associado opcionais, descrição, valor total, estado, transação de
origem para cancelamento/estorno, snapshot JSONB, autoria e versão.

`transacao_itens` guarda item de catálogo quando aplicável, descrição/unidade
fotografadas, quantidade `NUMERIC(24,8)`, valor unitário e total monetário. O
total é calculado no servidor e validado na transação.

`transacao_rateios_uvr` liga transação e UVR, com percentual ou valor, estado e
autoria. Toda atribuição de UVR, inclusive única, usará essa
tabela; assim a transação não precisa de `uvr_id` direto. A soma exata de rateios
e compatibilidade de associação exigem lock/validação transacional; CHECK valida
apenas valor positivo, percentual e modalidade exclusiva.

Transação concluída e seus itens/rateios são imutáveis. Correção gera evento e
cancelamento, estorno ou substituta. FKs históricas usam RESTRICT.

## 14. Patrimônio

Modelo futuro proposto:

| Tabela | Finalidade |
|---|---|
| `patrimonios` | identidade, classe, associação responsável, estado, condição e auditoria |
| `patrimonio_identificadores` | patrimônio, tipo, valor original/normalizado, fabricante/classe |
| `patrimonio_vinculos` | custódia UVR/associação, transferência e compartilhamento temporal |
| `patrimonio_eventos` | cadastro, alteração, transferência, baixa, reversão e fotografia |
| `patrimonio_documentos` | vínculo com metadado privado e categoria |
| `patrimonio_fotografias` | documento privado, finalidade, ordem e período |
| `patrimonio_bloqueios` | tipo, motivo, início/fim e autoria |

Número patrimonial é único por associação; placa e Renavam são únicos quando
informados; série depende de fabricante e classe. A combinação de tipo e valor
normalizado usa índices únicos parciais apropriados. Estados/condições e datas
têm CHECKs; transições, transferência e reversão exigem transação e evento.

As 38 colunas atuais permanecem somente no banco atual para migração. Rascunho
sem vínculos pode ser descartado; após ativação, RESTRICT e histórico permanente.

| Tabela | Conteúdo |
|---|---|
| `solicitacoes_alteracao` | tipo, módulo, objeto, solicitante, estado, risco, versão esperada e quatro snapshots JSONB |
| `solicitacao_eventos` | transições append-only, ator, justificativa, resultado e request ID |
| `solicitacao_mensagens` | mensagem, visibilidade, autoria e data; sem segredo |
| `solicitacao_aprovacoes` | etapa, decisão, aprovador, segregação e data |

## 16. Documentos privados e auditoria técnica

Foi aprovado o modelo C documental: `documentos_privados` como núcleo comum de
metadados e tabelas de vínculo por domínio. Campos: UUID público, provedor, chave
opaca única, nome seguro, extensão/MIME verificados, tamanho, SHA-256, estado,
retenção e auditoria. URLs temporárias nunca são persistidas.

`fc_documentos` permanece intacta por compatibilidade. Unificação/migração exige
nova etapa; não se cria FK retroativa. Tabelas patrimoniais, bancárias e de
solicitações referenciam o núcleo comum com permissões próprias.

`auditoria_tecnica` é append-only e guarda request ID, usuário, ação, módulo,
tipo/ID do objeto, associação/UVR quando aplicável, estados, justificativa,
instante, IP `INET`, agente resumido, resultado e JSONB sanitizado. Índices:
request ID, objeto+data, usuário+data, associação/UVR+data e resultado+data.
Retenção ainda será definida. Logs de aplicação não substituem esta trilha.

## 17. Histórico, delete e integridade

| Relação/categoria | Política proposta | Motivo |
|---|---|---|
| usuário → autoria histórica | RESTRICT | autoria não desaparece |
| entidade → eventos | RESTRICT/sem delete cotidiano | história permanente |
| rascunho → dependência técnica sem valor | CASCADE excepcional | descarte atômico aprovado |
| token de recuperação expirado | retenção técnica controlada | segredo temporário |
| catálogos referenciados | RESTRICT | fatos permanecem legíveis |
| vínculo opcional não histórico | SET NULL excepcional | somente se snapshot mantiver sentido |
| financeiro, associado, patrimônio, solicitação | sem exclusão após ativação | preservação funcional |
| arquivo privado | inativar metadado; remoção física por política | retenção/auditoria |

### 17.1 Matriz de constraints

| Regra | PostgreSQL direto | Serviço/trigger justificado |
|---|---|---|
| PK/FK, unicidade, código, valores e datas | PK/FK/UNIQUE/CHECK | não |
| um principal ativo | índice único parcial | não |
| período sem sobreposição | exclusion constraint possível | serviço se intervalo depender de estado |
| entidade ativa ligada a pai ativo | não por FK | transação com lock |
| última Administração Global | não | transação com lock |
| total de itens/rateios | não entre linhas | serviço transacional; trigger só se exigido após benchmark |
| transição de estado | parcialmente CHECK | serviço + evento |
| snapshot compatível com tipo | JSONB básico | validação por versão no serviço |
| imutabilidade histórica | privilégios/rotas | serviço e papel de banco futuro |

### 17.2 Matriz de índices

| Domínio | Índices principais | Risco controlado |
|---|---|---|
| usuários | username/e-mail normalizados, estado | UNIQUE já cria índice |
| autorização | FKs, perfil+validade, escopos ativos | evitar combinações raramente consultadas |
| associação/UVR | códigos, nomes normalizados, associação+estado, aliases | revisar seletividade de estado isolado |
| associados | CPF, número, nome, vínculos ativos, estado | dados sensíveis não entram em índice textual amplo |
| catálogo | códigos, nomes normalizados compostos, aliases | sem duplicar UNIQUE |
| financeiro | associação+período, conta+período, estado, origem, rateios | índices afetam escrita |
| patrimônio | identificadores normalizados, associação/UVR+estado, eventos | parciais para identificador não nulo |
| solicitações | estado+risco+data, objeto, solicitante, analisador | focar filas reais |
| auditoria | request, objeto+data, usuário+data | particionamento futuro, não agora |
| Fiscalização | preservar índices 001–011; revisar apenas com evidência | não alterar histórico |

| `fc_ocorrencias` | irregularidade do contrato | FK composta fiscalização/contrato, estados/prazos | preservar |
| `fc_ocorrencia_acompanhamentos` | evolução da ocorrência | estados e descrição, ordem temporal | append-only lógico |
| `fc_fiscalizacao_eventos` | histórico de fiscalização | transições/justificativa | append-only |
| `fc_medicoes` | versões de medição | competência, período, estado, atual única | preservar fluxo |
| `fc_medicao_itens` | itens medidos | quantidades, preço, excedente, único parcial | preservar |
| `fc_medicao_ajustes` | acréscimo/desconto/glosa | tipo e valor; vínculos ocorrência/fiscalização | preservar sem tratar glosa como sanção |
| `fc_medicao_documentos` | medição↔documento | categoria e vínculo ativo único | preservar |
| `fc_medicao_eventos` | histórico da medição | transições, justificativa e totais | append-only |
| `fc_atestes` | ateste da medição | número, estado, valor, encaminhamento | preservar; aprovação ≠ pagamento |
| `fc_ateste_notas_fiscais` | notas e documento privado | número/valor, duplicidade ativa | preservar upload privado |
| `fc_ateste_documentos` | ateste↔documento | categoria e vínculo ativo único | preservar |
| `fc_ateste_eventos` | histórico do ateste | transições, justificativa e valores | append-only |

Dependências externas ao módulo: `usuarios` em todas as autorias; nenhuma tabela
usa `role`/`uvr_acesso`; documentos dependem de `fc_documentos`. Perfis futuros
entram na autorização da aplicação, não em FKs retroativas. O módulo continua
global, com escopos por contrato/objeto atribuídos em estrutura específica
futura, com desenho físico a revisar na H2C.3B.

## 19. Dados estruturais

| Classe | Conteúdo |
|---|---|
| indispensável | controle de migrations, módulos/ações/permissões, tipos de escopo |
| mesma versão | perfis institucionais protegidos sem usuários; estados/eventos essenciais; `RECEITA`, `DESPESA`, `PRODUTO`, `SERVICO` |
| posterior | catálogos técnicos que não bloqueiam inicialização e módulos opcionais |
| proibido | usuários, associações, UVRs, associados, contas, catálogo operacional, patrimônio, contratos e demais dados reais |

Carga estrutural deve ser determinística e versionada. Idempotência não pode
ocultar divergência: código existente com conteúdo diferente é erro.

## 20. Ordem conceitual aprovada de criação

0. validar banco vazio e adquirir lock;
1. criar controle central de migrations;
2. criar catálogos técnicos independentes;
3. criar usuários/recuperação;
4. criar autorização sem escopos organizacionais;
5. criar associações/UVRs/aliases;
6. completar escopos organizacionais;
7. criar associados, vínculos e dados bancários;
8. criar documentos privados comuns;
9. criar catálogo operacional vazio;
10. criar contas, financeiro, itens e rateios;
11. criar patrimônio e históricos;
12. criar solicitações;
13. criar auditoria técnica;
14. reproduzir migrations 001–011 do módulo Fiscalização na ordem original;
15. carregar apenas dados estruturais aprovados;
16. executar validações finais de objetos, FKs, constraints e checksums.

Ciclos são evitados criando autorização básica antes de associação/UVR e seus
escopos depois; documentos comuns antes dos vínculos; eventos depois das
entidades. Autoria opcional durante bootstrap deve ser evitada por ator técnico
explicitamente auditado, cujo desenho físico será revisado na H2C.3B.

## 21. Módulos opcionais e legados

Auditoria funcional, documentos/entregas legados, EPI, Ouvidoria, pessoa mestre,
`produtos` e as demais tabelas H2C.2I ficam fora. Cada módulo opcional possui
prefixo/namespace, migrations, versão, checksum, dependências e testes próprios.
O núcleo nunca depende de módulo opcional; o opcional pode depender de uma
versão mínima explícita do núcleo.

## 22. Compatibilidade com o banco atual

| Conceito futuro | Atual | Instalação nova | Migração atual/risco |
|---|---|---|---|
| perfis/escopos | `role`, `uvr_acesso` | estruturas próprias | coexistência e comparação; alto |
| associação/UVR | textos dispersos | IDs e vínculos | saneamento/aliases; alto |
| associado | linha com textos/estado | cadastro + vínculos/histórico | CPF/duplicidade; alto |
| banco do associado | não comprovado na linha | estrutura própria | mapeamento humano; médio |
| catálogo | grupos/subgrupos/produtos_serviços textuais | hierarquia por ID | duplicidades/classificação; alto |
| financeiro | textos, associação/UVR e itens legados | IDs, snapshots e rateios | comparação de totais; crítico |
| patrimônio | tabela de 38 colunas | estruturas normalizadas | preservação e reconciliação; crítico |
| solicitações | versão A | fluxo/eventos/snapshots | coexistência; alto |
| documentos | estruturas diversas e `fc_documentos` | metadado comum + vínculos | retenção/permissão; alto |
| Fiscalização | 23 tabelas 001–011 | resultado equivalente | autoria INTEGER/BIGINT; médio |

A baseline nunca transforma esse banco. O projeto de migração adicionará
estruturas, mapeará, comparará resultados e encerrará fallbacks somente após
homologação.
